# Fork 仓库维护原则

## 概览

高质量开源贡献要求个人 fork 的默认分支持续充当上游镜像，而不是个人开发分支。PR 中出现本地工作文件、无关提交或陈旧历史，通常不是代码问题，而是分支边界和同步流程失控。

## 核心原则

- 默认分支只用于同步上游，不直接承载开发提交。
- 每项工作从最新上游默认分支创建独立特性分支。
- PR 只包含解决目标问题所需的提交和文件。
- 本地运行生成的会话、缓存、日志和工作目录必须由忽略规则隔离。
- 同步、清理和强制更新属于高风险操作，执行前必须确认远程、分支和工作区归属。

## 维护流程

### 贡献前诊断

先比较 fork 默认分支与上游默认分支的提交头和文件差异，再检查特性分支相对上游的实际改动。诊断结果应能回答三个问题：基线是否最新、历史是否纯净、变更是否聚焦。

### 污染修复

如果默认分支已包含个人提交或生成文件，应先保存仍需保留的工作，再恢复与上游一致的基线，最后从干净基线重新建立特性分支。来源给出了重置、清理和强制推送流程，但这些命令具有破坏性，不能在未确认备份、远程指向和变更所有权时机械执行。

### 预防机制

通过 `.gitignore` 隔离运行时文件，通过同步脚本固定上游更新步骤，并在 PR 前执行文件范围检查。自动化的目标是减少人为遗漏，而不是绕过对目标分支和差异范围的确认。

## 实践检查清单

- 当前分支是否从最新上游默认分支创建？
- PR 是否只包含当前议题相关文件？
- 是否误提交 Agent 工作区、日志、凭据或临时产物？
- 提交历史是否易于审查，没有混入同步提交或旧任务？
- 需要强制推送时，是否已确认目标远程和影响范围？

## 决策依据

保持默认分支纯净的直接收益是降低 PR 噪声、冲突和误提交风险。即使平台允许从污染分支继续开发，也应优先恢复清晰基线，因为审查成本和回滚成本会随无关历史快速增长。
